# Master-data cleansing and reconciliation

Profiling, rule-based cleansing and reconciliation of person and transaction master data before HCM load, executed on synthetic ADABAS data with an exception list and control totals.

| | |
|---|---|
| **Capability** | Master-data cleansing and reconciliation |
| **Why it matters to an SI implementing an HCM** | HCM Data Loader rejects orphaned foreign keys, invalid domains and duplicate source keys; finding them in the source first, with counts that reconcile, is what turns a load attempt into a load plan. |
| **Builds on** | `../tests/harness/adabas_sim.py`, `../tests/harness/fixtures.py`, `../03-data-model-data-dictionary/data-dictionary-hcm.md` (rule keys), `../docs/data-dictionary.md` |
| **Maturity** | Demonstrated on synthetic data (profile → rule → cleanse → reconcile runs here today and is drift-tested); payroll-specific relationship and effective-dating rules are (designed) |

## What the harness proves

| Question | Where the proof is |
|---|---|
| Nothing was lost or invented between extract and load | `reconciliation-report.md` "Record counts per file": in = loaded + held + rejected, per file |
| Every rule did something observable | "Outcome per rule": evaluated / passed / corrected / flagged / rejected |
| The transaction amount reconciles | "Control totals": `NCCONTRACT.PRICE` in = loaded + held + rejected |
| Two runs on the same data give the same loadable set | "Loadable-set content hashes" (SHA-256 per file), fixed seed and as-of date |
| The harness finds what was planted and nothing unplanned | "Injected defects versus detections": planted + baseline-fixture presence exceptions = detected, per rule; `--check` fails otherwise |
| Rules, dictionary and documentation agree | `--check` compares rule IDs with `cleansing-rules.md`; the 03 generator rejects rules keyed to unknown fields |

## Reproduce

```bash
# from the repository root
python3 fpps-hcm-modernization-deliverable/07-master-data-cleansing/harness/cleanse_reconcile.py          # regenerate sample-output/
python3 fpps-hcm-modernization-deliverable/07-master-data-cleansing/harness/cleanse_reconcile.py --check  # exit 1 on drift or an unbalanced control
```

## How an SI consumes this

1. Take `cleansing-rules.md` as the data-quality section of the HCM Data Loader mapping workbook: one row per rule, keyed to the dictionary field, with the default action. Decide per rule whether it becomes an HDL transformation (the `correct` rules), an HCM lookup or validation configuration (the domain rules), or a steward procedure (the `flag` rules).
2. Run the harness once to see the shape of the outputs, then replace `build_dirty_db()` with an extract reader for the real DDM files; the rule functions, reconciliation and report do not change. Keep `--check` in the pipeline so that a changed extract or rule is visible as a changed hash.
3. Put the reconciliation controls into the acceptance-test plan verbatim: record balance per file, per-rule counts, transaction amount total, distinct person count, loadable-set hash. Pair each with its post-load counterpart (worker validation report, payroll data validation report, balance exception report) as listed in `cleansing-approach.md` "Post-load verification".
4. Use `exceptions.csv` as the steward queue format: file, source key, rule, field, outcome, message. Load it into the BPM or ticketing tool the client uses for data stewardship and close each row before the wave is signed off.
5. Add the (designed) rules from `cleansing-rules.md` "Rules not demonstrated on the sample" once the estate's DDMs expose the fields: supervisor chain, department tree, position effective window, effective-date non-overlap, statutory identifiers.
6. Order HDL files by the relationship table in `../03-data-model-data-dictionary/data-model.md`: organisation, then position, then person, then transactions; fix each file's errors before loading the next.

## Synthetic data and scope

All data in this directory is synthetic: the harness starts from `tests/harness/fixtures.make_db()` and adds deterministic rows and injected defects with a fixed seed. No production system, production data, or FPPS source is used or required. FPPS statements are analogies to a Software AG Natural 9.x / ADABAS 8.6 estate (~7M lines of Natural, 100k+ modules, ~7,800 JCL jobs). `harness/cleanse_reconcile.py` is a validation and cleansing harness; it is never a rewrite target, and nothing here proposes converting Natural into Python or any other language.
