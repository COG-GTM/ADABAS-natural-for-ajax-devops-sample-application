The problem

Direct conversion already failed here. The buyer needs requirements, not a translation.

FPPS is Software AG Natural 9.x — roughly 7 million lines across 100,000+ modules — on ADABAS 8.6 and z/OS 2.5, driven by ~7,800 JCL jobs. It is not COBOL. A prior attempt to push the code through a general-purpose LLM converter produced output nobody could verify. The alternative quoted by a large integrator — interview-driven requirements gathering at roughly $30M — is slow, expensive, and still depends on institutional memory that is retiring.

What does not work

Line-by-line conversion

Natural source→LLM "translate"→Java / Python / C#→hope it matches
  • Copies every defect faithfully — including race conditions and duplicate-key generation that only show under multi-user load.
  • Rebuilds dead, unreachable, and training-only code because a converter cannot tell it apart from the business.
  • Produces a second system nobody understands, with no requirements to configure an HCM against.
  • Cannot be verified without production data, so the buyer has to trust rather than test.
VS
What this package does

Requirements-first extraction

Natural source→extract + cite→disposition→requirements baseline→Oracle HCM (SI)→reconcile
  • Every rule, edit, field, process, and interface is traced to the exact source line and scored for confidence.
  • Integrity behaviour becomes a requirement ("atomic decrement, unique key") that an HCM satisfies natively — not code to port.
  • Dead and unmappable logic is surfaced with evidence and routed to SME sign-off, so it is retired deliberately, not by accident.
  • Python exists only as the test harness that proves the HCM output equals legacy behaviour, on synthetic data anyone can rerun.

Sample ↔ FPPS analogy

Booking transaction ≈ pay/personnel transaction · message-code edits ≈ payroll validation edits · ADABAS DDMs ≈ personnel-payroll data model · record-hold integrity ≈ pay-run integrity · CRUISE16 ≈ core Natural service libraries · RDCRUISE ≈ Web FPPS presentation layer.

Why synthetic data matters

Every harness, fixture, and reconciliation on this page runs without production access. That is what makes the offer "run our pipeline on your slice and validate the output yourself" credible to a CIO and an ATO board.

The methodology

Five stages, one chain of evidence: from the source line to the reconciled HCM output.

Each stage produces artifacts the next stage consumes, and every artifact is regenerated from source by a checked-in tool with a drift gate. Nothing on this page is a hand-written claim about the code.

How Devin does it

Autonomous engineering sessions that read the estate, write the tools, and leave a reproducible trail.

Devin is not a translator. It is an autonomous software engineer that reads the Natural libraries the way a senior developer would — following CALLNAT chains, opening the DDMs, tracing a message code back to the edit that raises it — and then writes and tests the analyzers, generators, and harnesses that make each finding reproducible. Human reviewers (Cognition, SMX payroll SMEs, IBC) check the evidence, not a chat transcript.

1 · Comprehend

DeepWiki indexes the repository so anyone can ask "what raises 9918?" and get the answer with the source lines. Devin reads CRUISE16 (business logic) and RDCRUISE (Natural for AJAX presentation), the four DDMs, PDAs/LDAs, copycode, and the natdeploy*.xml STEPLIB chains.

2 · Instrument

Devin writes the static analyzer and generators as first-class, tested code. Library-qualified object identity, per-catalogue message-code reconciliation, symbol-owner attribution for field usage, and commented-out statement detection were all added because the real source demanded them — and each fix carries a fixture test.

3 · Parallelise

The ten capability directories were produced by parallel Devin sessions writing into stable, pre-scaffolded targets, then merged and cross-linked. The same fan-out pattern is the plan for FPPS scale Roadmap: partition by library, run in parallel, reconcile at the seams.

4 · Verify

Every generated table has a --check gate; the test suite fails if a committed artifact diverges from its generator. Devin Review then reviews Devin's own PR — the review rounds on this package caught parser edge cases (MOVE BY NAME, whole-view RESET, shadowed same-name objects) before a human ever looked.

5 · Disposition

Static findings are labelled as candidates with an evidence class and confidence, never as proof. At FPPS scale they are closed with Natural Predict/XRef, runtime traces, profiler data, JCL/scheduler data, ADABAS logs, and SME sign-off — the evidence plan is part of the package.

6 · Hand off

The SI receives requirements, acceptance criteria, an HCM Data Loader-oriented dictionary, BPMN flows, and a reconciliation harness that accepts their HCM's output. Cognition's Python never becomes the system of record; it is the test bench the SI runs against Oracle HCM.

Differentiator

The rule a naive converter loses — and the class of bug that silently corrupts a pay run.

The booking transaction CONEW-N is the sample's pay/personnel transaction. Its original implementation had two multi-user defects that no single-user unit test and no line-by-line translation would expose. Devin found both by reading the record-hold semantics, proved them with an interleaving simulator, and recorded them as an integrity requirement the HCM must satisfy — not as code to port.

Original behaviour

Read without a hold, then update

Two users read CRUISE-STATUS = 1 (one place left). Both pass the availability test. Both decrement and store. Result: two contracts for one place. Separately, CONTRACT-ID was computed as MAX+1 from a read that did not hold the highest record — two users compute the same key, and CONTRACT-ID is a descriptor, not a unique index, so both succeed.

Payroll analog: two personnel actions posting against the same pay period, or two pay records issued under one identifier. It passes every test until the first busy day.

Extracted requirement

Test-and-set under hold; serialised key generation

R1. FIND NCCRUISE WITH CRUISE-ID = ID-CRUISE-IN-N
  G1. GET NCCRUISE *ISN(R1.)          /* hold the record */
  IF VAL(CRUISE-STATUS) GT 0
    CRUISE-STATUS := CRUISE-STATUS - 1
    UPDATE (G1.)
  ELSE  MSG-NR := 9902               /* no longer available */

R2. READ (1) NCCONTRACT DESCENDING BY CONTRACT-ID
  UPDATE (R2.)                        /* hold MAX before +1 */
  NEWCONTRACTID := CONTRACT-ID + 1
STORE NCCONTRACT → END TRANSACTION    /* else BACKOUT */

In an HCM this is not custom code — it is a native requirement: atomic capacity decrement, unique enforced identifiers, all-or-nothing transaction. The requirement is what the SI configures; the harness is what proves they did.

A converter would have carried both defects into the new platform with perfect fidelity. Requirements-first extraction turns them into two lines of an acceptance criterion the HCM must pass — and the reconciliation harness below is exactly what catches an HCM that fails it (see check IN-01, duplicate CONTRACT_ID 500107, and IN-03, oversold capacity).
What not to migrate

The estate is full of things that do not map to an HCM. We find them, prove them, and route them to a decision.

Rebuilding dead code is the most expensive line item in any conversion, and the hardest to see. The disposition analyzer walks every executable path, reconciles message catalogues against the code that emits them, attributes field usage to its owning view, and separates comments from code. Each finding is a candidate with an evidence class and confidence; at FPPS scale it is closed with XRef, runtime traces, JCL/scheduler data, ADABAS logs, and SME sign-off.
