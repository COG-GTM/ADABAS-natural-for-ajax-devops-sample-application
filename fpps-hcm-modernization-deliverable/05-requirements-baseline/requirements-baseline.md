# Requirements baseline reconstructed from observed behaviour

This document is the artifact that replaces months of interview-driven requirements gathering. Instead of asking users what the system does and reconciling their recollections, every requirement below was reconstructed from what the shipped Natural source does, cross-checked against the executable tests in `tests/`, and tagged with the business rule(s) in [`../02-business-rule-extraction/business-rules.md`](../02-business-rule-extraction/business-rules.md) that evidence it. A payroll SI can verify any line of it against the repository in minutes and load it directly into a fit-gap workbook.

```
  Interview-driven baseline                     Source-derived baseline (this document)
  ─────────────────────────                     ──────────────────────────────────────
  workshops ──► notes ──► draft ──► review      source lines ──► rule (BR-nnn) ──► requirement (REQ-x-nnn)
  ──► SME dispute ──► rewrite ──► sign-off            │                │                 │
  evidence: memory, screenshots                       │                │                 └─► acceptance criterion
  disabled rules: invisible                           │                └─► confidence score      linked to tests/
  misapplied codes: invisible                         └─► --check: citation still valid?
  concurrency rules: invisible                  SME time spent only on the SME-required rows
```

Maturity: the baseline is Demonstrated for the Sunny Islands Cruise sample (every requirement cites executable source and most cite a passing test). The method — extraction, generated cross-checks, confidence scoring — is Designed for an estate of FPPS scale; nothing here claims FPPS source was analysed.

## How to read a requirement

| Field | Meaning |
|---|---|
| Statement | What the target system shall do, written as a testable obligation, in HCM vocabulary where the analogy holds (offering ≈ pay element / entitlement with a capacity; booking ≈ personnel-payroll transaction; customer ≈ person record) |
| Rationale | Why the behaviour exists and what goes wrong without it |
| Source evidence | `path:start-end` citations into the shipped source and `tests/` — every one opened and validated by `../02-business-rule-extraction/generate_rule_evidence.py --check` |
| Linked rules | Rule identifiers from 02 |
| HCM fit | standard (delivered behaviour), configured (delivered object plus set-up), extension (fast formula / custom object), integration (interface or load), out of scope |
| Disposition | carry / replace-with-standard-HCM / redesign / retire / SME-required |
| Maturity | Demonstrated (executes in `tests/` today), Designed (specified, no executable check yet), Roadmap (depends on SME or FPPS-scale input) |

## Integrity requirements (REQ-I)

These are the requirements a source-to-source converter loses: they are expressed in the sample as ADABAS hold logic, and a converter that copies read-then-write into application code silently drops them. Pay-run analogy: the entitlement balance a payroll run decrements must be decremented exactly once per approved transaction, and every generated transaction number must be unique, no matter how many operators or batch streams run at once.

### REQ-I-001 — Capacity is decremented atomically under contention

| Field | Value |
|---|---|
| Statement | When two or more transactions attempt to consume the last free place of the same offering concurrently, exactly one shall succeed and the others shall receive the "no longer available" outcome. For an offering with N free places, N concurrent or sequential attempts shall succeed and all further attempts shall fail; the free-place count shall never go below zero. The check and the decrement shall be performed on a locked, current copy of the record. |
| Rationale | The pre-refactor service read the count without a lock, so two users each saw one place and both booked it (overbooking). The refactor re-reads the record in hold before test-and-set. Executable proof of both the defect and the fix exists. |
| Source evidence | `SunnyIslands/Natural-Libraries/CRUISE16/Subprograms/CONEW-N.NSN:79-92`, `SunnyIslands/Natural-Libraries/CRUISE16/Subprograms/CONEW-N.NSN:133-138`; `tests/test_concurrency.py:24-45`, `tests/test_concurrency.py:68-97`, `tests/test_concurrency.py:129-141`; `tests/test_source_conformance.py:35-43`; `docs/concurrency-refactor.md:45-77` |
| Linked rules | BR-006 |
| HCM fit | standard (row-level locking and balance adjustment inside one transaction) — the requirement is on the outcome, not on reproducing ADABAS hold logic |
| Disposition | carry |
| Maturity | Demonstrated |
